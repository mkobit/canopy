# JSON-RPC IPC Schema Baseline & API Compatibility Verification Design

**Date:** 2026-08-01  
**Status:** Proposed  
**Beads Task:** `canopy-pf0.4`

## 1. Overview & Goals

Canopy currently validates API compatibility for three protocol transports in `tools/check-api-compatibility.ts` and `@canopy/api-adapter`:

1. GraphQL SDL (`GRAPHQL_SDL_SCHEMA`, `graphql.graphql`)
2. Connect-Web & gRPC Protobuf SDL (`PROTO_SERVICES_SDL`, `connect.proto`)
3. WebAssembly Interface Type specification (`CANOPY_WIT_SPECIFICATION`, `plugin.wit`)

Task `canopy-pf0.4` integrates JSON-RPC 2.0 IPC schema contracts (defined in `@canopy/api-adapter/src/ipc/ipc-schema.ts`) into the automated compatibility verification suite as the 4th protocol transport (`ipc`).

### Primary Objectives

- Generate a canonical OpenRPC 1.3 specification (`JSON_RPC_IPC_SPECIFICATION`) from Zod schemas and IPC method/error definitions.
- Maintain a baseline snapshot under `packages/api-adapter/schema-baselines/ipc-openrpc.json`.
- Implement `checkIpc()` in `tools/lib/api-compatibility-checker.ts` to detect breaking changes (method removals, parameter removals/tightening, result property drops, error code renumbering/removal).
- Support `--target ipc` and `--protocol ipc` waivers in `tools/check-api-compatibility.ts`.
- Update `approved-breaking-changes.schema.json` and `docs/architecture/api-compatibility-policy.md`.
- Add test coverage in `schema-baselines.test.ts` and `api-compatibility.test.ts`.

## 3. Specification & Baseline Generation

### `packages/api-adapter/src/ipc/ipc-openrpc-spec.ts`

- Constructs an OpenRPC 1.3 spec object containing:
  - `openrpc`: `"1.3.2"`
  - `info`: `{ title: "Canopy IPC Protocol", version: "0.1.0" }`
  - `methods`: Mapping of each method in `IPC_METHODS` with `paramStructure: "by-name"`, request parameter schemas, and result payload schemas derived via Zod schema reflection (`z.toJSONSchema`).
  - `errors`: List of error definitions from `JSON_RPC_ERROR_CODES`.
- Generates canonical JSON text with sorted keys and 2-space indentation.
- Exports `JSON_RPC_IPC_SPECIFICATION`.
- Re-exported via `packages/api-adapter/src/ipc/index.ts` and `packages/api-adapter/src/index.ts`.

### `packages/api-adapter/schema-baselines/ipc-openrpc.json`

- Baseline snapshot file with the header banner `/* AUTOGENERATED BASELINE FILE - DO NOT EDIT MANUALLY */` (or stored as a JSON header field).
- Updated during `bun tools/check-api-compatibility.ts --update-baselines`.

## 4. Breaking Change Detection Logic (`checkIpc`)

`checkIpc(liveSchemaJson: string, baselineSchemaJson?: string): readonly Violation[]` checks:

1. **`METHOD_REMOVAL`**: Baseline contains a method in `methods` array that is missing in `liveSchema`.
2. **`ERROR_CODE_REMOVAL`**: Baseline defines an error code in `errors` array that is missing or renumbered in `liveSchema`.
3. **`PARAM_REMOVAL`**: Baseline parameter present in method request schema is removed in `liveSchema`.
4. **`PARAM_TIGHTENING`**: Parameter in baseline was optional, but in `liveSchema` is marked required.
5. **`RESULT_PROPERTY_REMOVAL`**: Return payload schema property present in baseline is missing in `liveSchema`.

## 5. Adversarial review and mitigations

### 1. Resource and performance overhead

- **Risk:** Reflecting Zod schemas to JSON Schema dynamically during `check-api-compatibility` or baseline loading could slow down CI or `bun run lint`.
- **Mitigation:** `JSON_RPC_IPC_SPECIFICATION` is evaluated at import time as a pre-built static string or memoized constant. The compatibility check executes string parsing and comparison in under 15ms.

### 2. Failure modes and edge cases

- **Risk 1:** Zod schema output formatting variations across Node/Bun or Zod versions could produce non-deterministic JSON diffs in baseline tracking.
- **Mitigation:** Implement a recursive object key-sorting function prior to JSON stringification to ensure key ordering is strictly deterministic regardless of execution environment.
- **Risk 2:** Unhandled `z.passthrough()` or `z.unknown()` types causing invalid or missing JSON Schema structures.
- **Mitigation:** Ensure fallback JSON Schema types (e.g. `{}` or `{"type": "object"}`) are properly handled and normalized in `ipc-openrpc-spec.ts`.

### 3. Security and isolation

- **Risk:** Exposure of sensitive internal path names or system environment variables in baseline snapshot header banners.
- **Mitigation:** Baseline files strip environment variables, system user names, and absolute OS file paths before saving.

### 4. Migration and backward compatibility risks

- **Risk:** Existing waiver files or CI checks break due to target/protocol union expansion.
- **Mitigation:** Default `--target` remains `'all'`. `approved-breaking-changes.schema.json` schema validation allows `"ipc"` as a valid `protocol` alongside `'graphql'`, `'connect'`, `'wit'`, and `'all'`.
