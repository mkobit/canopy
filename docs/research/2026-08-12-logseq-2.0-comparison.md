# Logseq 2.0 (DB version) vs Canopy: a foundational-bets comparison

> Type: research / external evaluation
> Date: 2026-08-12
> Status: frozen snapshot
> Purpose: test Canopy's foundational architectural bets against Logseq's DB-version rewrite, and say plainly where Logseq's choices should make us reconsider ours and where Canopy is defensibly different for its goals

---

## Context

Logseq shipped the first public beta of its database version ("Logseq 2.0", tagged `2.0.1`) on 2026-07-13, ending a roughly four-year rewrite away from its founding Markdown-files-as-source-of-truth model ([kompozy.io](https://kompozy.io/news/logseq-2-0-db-version-beta), [Wikipedia: Logseq](https://en.wikipedia.org/wiki/Logseq)).
The Canopy maintainer, after looking at that rewrite, is questioning several of Canopy's foundational bets, so this document tests each bet against what Logseq actually built.

This is a fresh, bet-by-bet reconsideration.
It complements the earlier and broader [2026-08-03 Logseq DB vs Canopy comparison](2026-08-03-logseq-db-vs-canopy-architecture.md), which surveyed sync, query, plugins, and agent access; it does not restate that doc.
Where the two overlap (sync, query) the conclusions agree, and this doc cites the newer 2026-07-13 beta facts.

Canopy's five foundational bets, as stated in the design corpus, are the frame for the comparison:

1. "Everything is a node" and meta-circular schema — `NodeType`, `EdgeType`, `PropertyType`, `ViewDefinition`, `QueryDefinition`, `RendererDefinition` are themselves nodes in the graph, editable at runtime ([core-data-model §6](../design/2026-02-06-core-data-model.md), `packages/graph/src/system.ts`)
2. Event log as the sole persisted source of truth; graph state is a rebuildable projection (CQRS); no CRDT; history and time-travel fall out of the log ([event-log-storage-and-sync](../design/2026-07-03-event-log-storage-and-sync.md))
3. Rendering decoupled from content storage; content nodes hold pure properties, rendering resolved via `ViewDefinition`/`RendererDefinition` nodes referencing WASM plugins ([AGENTS.md invariant 10](../../AGENTS.md))
4. Query engine as a DSL/pipeline with a stubbed Cypher/GQL direction ([query-engine](../design/2026-02-08-query-engine.md))
5. Functional/immutable/branded-type discipline; storage backends are dumb `EventLogStore` carriers with no conflict logic ([bounded-contexts](../architecture/bounded-contexts.md), `packages/graph/src/event-log.ts`)

### A note on source quality

Logseq has not published a formal design document for the DB version's sync or storage internals; the community itself has noted this scarcity ([discuss.logseq.com: DB syncing thread](https://discuss.logseq.com/t/seflhosted-logseq-db-synching/34537)).
The most technical source available is [DeepWiki's `logseq/logseq` wiki](https://deepwiki.com/logseq/logseq), which is machine-generated from the ClojureScript source at a pinned commit; its claims are grounded in code but are a secondary reading, not a primary statement from the Logseq team.
The official [`db-version.md`](https://github.com/logseq/docs/blob/master/db-version.md) documents the user-facing data model well but says little about sync internals.
Every claim below is attributed; claims resting on DeepWiki's reading of source rather than an official statement are flagged inline.

## Logseq 2.0 as researched

### Data model

Logseq's DB version runs an in-memory [DataScript](https://github.com/tonsky/datascript) database — a Datalog engine over an entity-attribute-value (EAV) datom store — persisted to SQLite in the browser's Origin Private File System (OPFS) or Electron's local filesystem ([DeepWiki: schema/validation](https://deepwiki.com/logseq/logseq/4.2-database-schema-and-validation), [DeepWiki: repo management](https://deepwiki.com/logseq/logseq/4.3-repository-and-graph-management)).
Pages and blocks are unified into one concept, a "node", referenced uniformly with `[[ ]]`; a block becomes a page-like node by tagging it ([`db-version.md`](https://github.com/logseq/docs/blob/master/db-version.md)).
Hierarchy is stored relationally as datom attributes — `:block/parent` and `:block/page` are indexed `:db.type/ref` attributes, `:block/refs` and `:block/tags` are cardinality-many refs ([DeepWiki: schema/validation](https://deepwiki.com/logseq/logseq/4.2-database-schema-and-validation)).

### Typed properties and closed values

Properties are strongly typed with a schema per property: `:logseq.property/type`, `:db/cardinality` (`:db.cardinality/one` or `:db.cardinality/many`), `:property/closed-values` (an enum restricting allowed values), and visibility flags (`:public?`, `:hide?`) ([DeepWiki: property system](https://deepwiki.com/logseq/logseq/3.2-property-system)).
The user-facing types are Text, Number, Date/DateTime, Checkbox, URL, and Node (a typed reference to another node, optionally filtered by tag); Number/Date/Node/URL/Asset values are stored as references or real typed values, not strings, so numeric sort and date repetition work correctly ([`db-version.md`](https://github.com/logseq/docs/blob/master/db-version.md)).
Closed values (enums) are supported only for `:default`, `:number`, and `:url` types ([DeepWiki: property system](https://deepwiki.com/logseq/logseq/3.2-property-system)).
Validation is enforced with [Malli](https://github.com/metosin/malli) schemas at transaction and import time ([DeepWiki: schema/validation](https://deepwiki.com/logseq/logseq/4.2-database-schema-and-validation)).

### Tags as classes; how "meta" the model is

Tags are redesigned as classes: a tag carries "tag properties" that every node bearing the tag inherits, and tags support multiple inheritance through an `Extends` property, so classes form a hierarchy ([`db-version.md`](https://github.com/logseq/docs/blob/master/db-version.md)).
Core features are themselves built-in tags/classes — `#Task`, `#Query`, `#Card`, `#Template`, `#Journal`, `#Asset` — which means schema, stored queries, and templates live as tagged entities inside the same database as content, not as a separate configuration layer ([`db-version.md`](https://github.com/logseq/docs/blob/master/db-version.md)).
Views (table, list, gallery, with filter/sort/group) are stored as queryable data structures too ([`db-version.md`](https://github.com/logseq/docs/blob/master/db-version.md)).
So Logseq's model is "meta" at the content-and-schema layer: classes, queries, and views are data — but the class system itself is a fixed built-in vocabulary of DataScript attributes, not a user-redefinable metatype.

### Storage and source of truth

The SQLite database is now canonical; Markdown files are no longer the source of truth ([discuss.logseq.com: OG vs DB FAQ](https://discuss.logseq.com/t/logseq-og-markdown-vs-logseq-db-sqlite/34608)).
Markdown export still exists but is lossy — it cannot capture block properties or timestamps — and the only fully faithful, editable export is EDN, which the team frames as "the spiritual successor to Markdown's openness" while conceding it is less user-friendly and not yet recommended as a sole backup ([`db-version.md`](https://github.com/logseq/docs/blob/master/db-version.md), [kompozy.io](https://kompozy.io/news/logseq-2-0-db-version-beta)).
This provoked the "file over app" backlash: long-time users who valued plain-text file ownership objected, and Logseq split into two products — "Logseq OG" (file-based, maintained for security/Electron but frozen on features) and the DB version (keeps the name and the roadmap) ([kompozy.io](https://kompozy.io/news/logseq-2-0-db-version-beta), [discuss.logseq.com: too drastic?](https://discuss.logseq.com/t/database-version-too-drastic-choice/20346)).

### Sync and conflict resolution

Sync ("RTC", real-time collaboration) is a paid, invite-only, alpha feature with per-graph end-to-end encryption; the server is self-hostable but closed-source ([`db-version.md`](https://github.com/logseq/docs/blob/master/db-version.md), [kompozy.io](https://kompozy.io/news/logseq-2-0-db-version-beta)).
The mechanism, per DeepWiki's reading of the source (flagged: not an official statement), is an operation-log model, not a CRDT and not operational transform:

- Local edits are captured by a `db-listener` and written as discrete operations into a separate `client_ops` SQLite database, so pending writes survive offline ([DeepWiki: DB worker and RTC](https://deepwiki.com/logseq/logseq/4.1-layout-and-theming))
- A throttled flow pushes batched ops to the server; remote transactions arrive over WebSocket and are applied by `apply-remote-txs!` ([DeepWiki: DB worker and RTC](https://deepwiki.com/logseq/logseq/4.1-layout-and-theming))
- Conflict resolution is a re-basing approach: incoming remote transactions establish a baseline and pending local transactions are replayed against it, implying server-authoritative ordering rather than a lattice merge; a checksum of local state is maintained and updated per transaction ([DeepWiki: DB worker and RTC](https://deepwiki.com/logseq/logseq/4.1-layout-and-theming))
- On conflict or large divergence, a special exception triggers a full graph pull as a fallback ([DeepWiki, flagged as inference](https://deepwiki.com/logseq/logseq/4.1-layout-and-theming))

The headline fact: Logseq built genuine "like Google Docs" real-time multi-user collaboration and did **not** use a CRDT for the graph data; it used an op-log plus server-mediated rebase ([DeepWiki: DB worker and RTC](https://deepwiki.com/logseq/logseq/4.1-layout-and-theming)).

### Query

Querying is DataScript/Datalog directly against the in-memory datom store, which doubles as both the query engine and the live application state — a mature, indexed engine reused rather than built ([DeepWiki: schema/validation](https://deepwiki.com/logseq/logseq/4.2-database-schema-and-validation)).

### History and versioning

There is no general edit-history or time-travel feature in the DB version.
Task status changes keep a per-block status-history property, and deleted pages (not blocks) are soft-deleted into a 30-day recycle bin, but there is no point-in-time reconstruction of arbitrary past graph states ([`db-version.md`](https://github.com/logseq/docs/blob/master/db-version.md)).

### Migration story and rollout

The rewrite was planned from roughly late 2022 and did not reach beta until 2026-07-13 — about four years, during which most other feature development (including AI work started in 2023) stalled, the last file-version release sat from 2024-04-23 for nearly a year, and community threads openly questioned whether the project was still alive ([solanky.dev / Medium: migration journey](https://medium.com/@solanky/logseq-migration-journey-challenges-delays-and-hopes-473fa7b8608b), [discuss.logseq.com: why the DB version](https://discuss.logseq.com/t/why-the-database-version-and-how-its-going/26744)).
Migration from a file graph runs an import that converts tags to class entities, infers property types from values, and validates the result with Malli ([DeepWiki: schema/validation](https://deepwiki.com/logseq/logseq/4.2-database-schema-and-validation)).
The DB version and its sync ship with an explicit data-loss warning and a recommendation to back up the SQLite file ([`db-version.md`](https://github.com/logseq/docs/blob/master/db-version.md)).

## Canopy as-is

Canopy is a single-user, multi-device, offline-first personal knowledge graph, pre-1.0, with no real users or vaults yet.
Its model:

- Three structural primitives — node, edge, graph — with branded UUIDv7 IDs and readonly, immutable values ([core-data-model §1–2](../design/2026-02-06-core-data-model.md))
- Meta-circular type system: the node that defines the node-type type has itself as its type, and this self-reference covers edge types, property types, namespaces, queries, views, templates, and renderers ([`packages/graph/src/system.ts`](../../packages/graph/src/system.ts))
- Event log is the sole persisted truth; the `Graph` is a pure projection; conflict resolution is per-property last-writer-wins with an eventId tiebreak, additive edges, and permanent tombstones, applied during projection — "CRDT semantics without a CRDT library" ([event-log-storage-and-sync §4, §6](../design/2026-07-03-event-log-storage-and-sync.md))
- A single write path, `GraphSession.commit` (validate → append → incremental convergent projection → notify); five dumb `EventLogStore` backends (in-memory, IndexedDB, SQLite, file, HTTP) implement a two-method port with no graph awareness ([bounded-contexts](../architecture/bounded-contexts.md), [`event-log.ts`](../../packages/graph/src/event-log.ts))
- A branded, eventId-derived `revision` token for optimistic concurrency, and a `DraftSession` overlay that rejects concurrent modifications rather than merging ([`revision.ts`](../../packages/graph/src/revision.ts), [`draft-session.ts`](../../packages/graph/src/draft-session.ts))
- Query engine: a typed pipeline IR with a naive in-memory executor now backed by an in-memory read-model index, GQL/Cypher still a stub ([query-engine §5–6](../design/2026-02-08-query-engine.md), [`packages/queries/src/engine.ts`](../../packages/queries/src/engine.ts))
- The no-CRDT decision was re-examined and reaffirmed on 2026-08-12 in PR #446's CRDT-vs-event-log ADR

## Axis-by-axis comparison

### A. Core data model — everything-is-a-node / meta-circular vs block+property EAV

**Logseq**: pages and blocks unified into "node"; typing via tags-as-classes with `Extends` inheritance; classes, queries, views, and templates are tagged entities in the same DataScript store, but the class machinery itself is a fixed set of built-in attributes, not user-redefinable ([`db-version.md`](https://github.com/logseq/docs/blob/master/db-version.md), [DeepWiki: property system](https://deepwiki.com/logseq/logseq/3.2-property-system)).

**Canopy**: unifies further — not only is content a node, the type system is nodes, and metatypes are self-describing (`NodeType`'s type is `NodeType`), so users can define new node/edge/property types at runtime through the type-creation control plane ([core-data-model §6](../design/2026-02-06-core-data-model.md)).

**Verdict — does this challenge Canopy's bet? Partly, on ergonomics, not on soundness.**
Logseq is independent evidence that the direction is right: a shipping, popular tool converged on node-unification and on schema-as-data (classes/queries/views as tagged entities).
That is a meaningful validation of Canopy's instinct, not a refutation.
But Logseq also shows a lighter point in the design space: tags-as-classes with property inheritance is incrementally adoptable and cheap to author, whereas Canopy's formal `NodeTypeDefinition`/`PropertyType` registry is heavier to author for the same everyday outcome ("give this thing a due date").
Canopy's full meta-circularity (redefinable metatypes) buys genuine power Logseq lacks — importing external vocabularies, user-authored edge types, runtime schema evolution as replayable migration events — and for a graph whose premise is "the schema is data", that power is the point, not gold-plating.
The reconsideration is narrow and real: **authoring UX**.
Canopy should make sure the control plane can express a Logseq-style "tag carries inherited properties" pattern without ceremony, or it will feel heavyweight next to Logseq for the common case.
This is directly relevant to the open per-domain-namespace question (`canopy-6cz`).
Risk of ignoring: the meta-circular model stays elegant but authoring-hostile, and the everyday "just tag it" path never gets as smooth as Logseq's.

### B. Storage and source of truth — event-log CQRS vs DB-as-truth

**Logseq**: the SQLite/DataScript database is the canonical store; Markdown export is lossy; the fully faithful export (EDN) is a secondary, less-friendly artifact derived from the DB, and abandoning files-as-truth was contentious enough to fork the product ([discuss.logseq.com: OG vs DB FAQ](https://discuss.logseq.com/t/logseq-og-markdown-vs-logseq-db-sqlite/34608), [kompozy.io](https://kompozy.io/news/logseq-2-0-db-version-beta)).

**Canopy**: the event log is the canonical, portable artifact — plain JSON events you can `cat` and `rg` — and the materialized graph is a disposable, rebuildable projection ([event-log-storage-and-sync](../design/2026-07-03-event-log-storage-and-sync.md)).

**Verdict — this reinforces Canopy's bet; Logseq's pain is exactly what Canopy's model avoids.**
Logseq's "file vs DB" lesson maps cleanly onto Canopy's "event-log vs materialized-view" split, and Canopy landed on the better side of it.
Logseq's controversy is fundamentally that the _canonical_ representation became an opaque database while the _portable_ representation (Markdown) became lossy — users lost the property that their truth was inspectable and hand-editable.
Canopy's canonical representation is the opposite: the truth is the human-readable append-only log, and the opaque-ish thing (the in-memory projection) is the disposable derivative.
Canopy gets DB-like queryability (a materialized projection with indexes) _and_ file-like portability/inspectability (the log), instead of trading one for the other.
One honest cost to name: Logseq's DB-as-truth gives it a mature indexed store for free, while Canopy's log-as-truth means the read side is a projection it must index itself (see axis D).
And Canopy should heed the second half of Logseq's lesson — keep the portable format lossless and first-class from day one, because Logseq's backlash was as much about _lossy_ export as about the file→DB shift.
Canopy's log is already lossless by construction; the discipline is to never let a "materialized snapshot for speed" optimization quietly become a second, authoritative, non-portable store.
Risk of ignoring: none to the core bet; the watch-item is snapshot/compaction work (an open question in both the event-system and storage docs) not eroding the "log is the only truth" invariant.

### C. Sync and conflict — event reconciliation + per-property LWW vs Logseq's op-log rebase

**Logseq**: an operation log (`client_ops`) plus server-authoritative rebase over WebSocket, with full-graph-pull as the divergence fallback — **not a CRDT** — to serve real-time multi-user collaboration ([DeepWiki: DB worker and RTC](https://deepwiki.com/logseq/logseq/4.1-layout-and-theming)).

**Canopy**: an append-only event log with per-property LWW resolved in projection, per-device single-writer folders for file sync, per-device watermarks for reconciliation, and optimistic-concurrency rejection (not merge) at the draft layer — also not a CRDT, for single-user multi-device eventual sync ([event-log-storage-and-sync §4–6](../design/2026-07-03-event-log-storage-and-sync.md), [`draft-session.ts`](../../packages/graph/src/draft-session.ts)).

**Verdict — this is the strongest validation of Canopy's no-CRDT bet, and it comes from the hardest case.**
The maintainer's worry was presumably: "if Logseq does real-time collaboration and it works, does that undercut Canopy's decision to reject CRDTs?"
The answer is the reverse.
Logseq built the exact use case a CRDT is supposedly for — Google-Docs-style real-time multi-writer editing — and still did not adopt a CRDT for its graph data; it chose an operation log with server-mediated rebase and a full-pull fallback ([DeepWiki: DB worker and RTC](https://deepwiki.com/logseq/logseq/4.1-layout-and-theming)).
Two independent teams solving conflict resolution over structured graph data both concluded that op-log-plus-ordering beats a CRDT backbone; that is corroboration, not challenge.
The fair, non-rubber-stamp caveats:

- Logseq's model is server-authoritative (a central rebase point), which is genuinely simpler to reason about for real-time convergence than Canopy's fully decentralized, serverless file-folder reconciliation — Canopy pays for serverlessness with a convergence invariant it must prove (and does, via a property-based test), whereas Logseq offloads ordering to a server
- Logseq _does_ achieve true concurrent multi-user editing; Canopy explicitly does not, and resolves same-property races by LWW with the loser preserved in history rather than by merge — a real capability difference, honestly a loss, but a loss Canopy consciously accepted for a single-user product
- Neither uses a CRDT, so this axis does not argue for reintroducing one; if Canopy ever needs character-level real-time merge of one text property, the reaffirmed answer is Option C from PR #446 — a per-property `crdt-text` merge strategy, not a CRDT backbone

Risk of ignoring: none. The bet holds and is strengthened. The only thing to _not_ do is conclude from Logseq's success that "real-time collaboration requires a CRDT" — Logseq is the counterexample.

### D. Query engine — Canopy's DSL/Cypher direction vs Datalog/DataScript

**Logseq**: DataScript, a mature indexed in-memory Datalog engine, serving as both query layer and application state store — reused, not built ([DeepWiki: schema/validation](https://deepwiki.com/logseq/logseq/4.2-database-schema-and-validation)).

**Canopy**: a typed pipeline IR plus a naive scan executor with an in-memory read-model index, and an explicit, still-open decision to eventually parse ISO GQL/Cypher into that IR ([query-engine §4, §10](../design/2026-02-08-query-engine.md)).

**Verdict — this is the axis where Logseq should make Canopy genuinely reconsider.**
Canopy's underlying model is already EAV/graph-shaped — nodes with typed property maps and typed edges — which is precisely the shape Datalog was designed to query.
Logseq demonstrates that a Datalog engine (DataScript specifically) fits a node/EAV model natively, is indexed and battle-tested, and can double as the live read model, whereas Canopy's plan is to hand-write a GQL/Cypher parser and its own planner and indexes ([query-engine §4 open question, §6](../design/2026-02-08-query-engine.md)).
The prior [2026-08-03 doc](2026-08-03-logseq-db-vs-canopy-architecture.md) already flagged DataScript as prior art and measured a linear-scan performance bend around ~10k nodes; this doc sharpens the recommendation from "consult it" to "reconsider the target language and engine before building the parser".
The specific reconsideration:

- Datalog fits an EAV node model more naturally than GQL/Cypher, which is oriented toward labeled-property-graph traversal syntax; Canopy would be adopting GQL partly for standards-compliance optics rather than model-fit
- A Datalog engine over the projected graph could be the read model, collapsing the "query IR + planner + index" work Canopy is otherwise signing up to build from scratch
- The GQL/Cypher direction is the least-committed of Canopy's bets (stubbed, `Status: draft`, no bead, no OpenSpec change), so it is the cheapest to revisit before real investment

This does not mean adopt DataScript wholesale — it is ClojureScript, and Canopy is strict TypeScript with a functional/immutable discipline; a direct dependency is unlikely to fit.
But the _shape_ of the answer (a Datalog-style engine over the node model) deserves a real evaluation against the GQL plan before the parser is written.
Risk of ignoring: Canopy hand-rolls a GQL parser, planner, and index layer — months of work — to reach where a Datalog engine over its own EAV-shaped data would start, and gets a query language that fits its model less naturally than the alternative it skipped.

### E. Typed properties and schema control plane — PropertyType/NodeType-as-nodes vs property/class system

**Logseq**: strongly-typed properties with per-property schema — type, cardinality (one/many), closed values (enums), visibility — and classes (tags) that inject inherited properties, all validated by Malli, all shipping today ([DeepWiki: property system](https://deepwiki.com/logseq/logseq/3.2-property-system), [`db-version.md`](https://github.com/logseq/docs/blob/master/db-version.md)).

**Canopy**: `PropertyType` and `NodeType` are first-class metatype nodes with Zod-schema validation, but `PropertyType` constraints (format, range, enum) and cardinality are still explicitly open questions, not implemented ([core-data-model §7, §10](../design/2026-02-06-core-data-model.md)).

**Verdict — Canopy's architecture is more powerful; Logseq's shipped feature set is a concrete spec for the gaps Canopy hasn't filled.**
Canopy's schema-as-nodes approach is strictly more expressive than Logseq's fixed built-in class attributes — Canopy can define new property types and edge types at runtime and import external vocabularies, which Logseq's built-in class machinery cannot.
So the architectural bet is not challenged; it is ahead.
But Logseq has _shipped_ the property features Canopy has only sketched, and its choices are a ready-made specification:

- Cardinality (`one` vs `many`) is a first-class per-property attribute in Logseq; Canopy models arrays in `PropertyValue` but has no declared cardinality on `PropertyType` — worth adopting the explicit declaration
- Closed values (enums) are shipping in Logseq and are Canopy's open question 4 ("constraint validation on PropertyTypes") — Logseq's `:property/closed-values` (a restricted vector of allowed value maps) is a concrete design to borrow
- Typed references (Logseq's "Node" property type, optionally filtered by tag) match Canopy's `NodeId` property values, and the "filtered by target type" constraint is a validation feature Canopy could specify
- Property-choices-scoped-to-a-class is a useful pattern for Canopy's namespace/type-scoped vocabularies

Risk of ignoring: low architectural risk, but Canopy's typed-property surface stays thinner than a shipping competitor's, and the open constraint-validation questions linger without a reference design when Logseq has already published one worth copying.

### Bonus axis: rendering decoupled from content (Canopy bet 3)

Logseq renders natively and does not decouple rendering into graph-resident renderer definitions, so there is little direct comparison.
Canopy's bet 3 (rendering resolved via `ViewDefinition`/`RendererDefinition` nodes and WASM plugins) is more ambitious and remains largely aspirational in code.
Logseq neither validates nor challenges it; it is orthogonal to the DB-version rewrite.
No verdict change.

## Where to reconsider vs where Canopy is defensibly different

### Genuinely warrants reconsideration

- **Query engine direction (axis D)** — evaluate a Datalog-style engine over the projected node model before building a GQL/Cypher parser and bespoke planner; the model is already EAV-shaped, DataScript is direct prior art, and this is Canopy's least-committed bet
- **Typed-property feature gaps (axis E)** — adopt explicit cardinality and closed-value (enum) constraints on `PropertyType`, using Logseq's shipped `:db/cardinality` and `:property/closed-values` as the reference design; this closes core-data-model open question 4
- **Authoring ergonomics of the schema control plane (axis A)** — ensure the meta-circular type system can express Logseq's lightweight "tag carries inherited properties" pattern without heavy ceremony, so the common case is as smooth as Logseq's; ties into `canopy-6cz`

### Defensibly different / bet holds

- **Storage and source of truth (axis B)** — the event log as the portable, inspectable canonical artifact is the _right_ side of the exact trade that caused Logseq's "file over app" fork; Canopy gets queryability and portability instead of trading one for the other
- **Sync and no-CRDT (axis C)** — reaffirmed, and now corroborated by Logseq choosing op-log-plus-rebase over a CRDT _even for real-time multi-user collaboration_; do not read Logseq's collab success as a reason to add a CRDT
- **Meta-circular schema (axis A, architecture)** — more powerful than Logseq's fixed class machinery; validated in direction by Logseq's schema-as-data convergence; the only issue is authoring UX, not soundness
- **Immutable/branded discipline and dumb storage backends (bet 5)** — Logseq's dumb server (a store that does not understand the graph, with the client reconciling) is the same instinct as Canopy's dumb `EventLogStore`; no challenge

### What Logseq learned the hard way that Canopy can avoid

- **A multi-year big-bang rewrite that freezes everything else is a trust hazard** — Logseq's ~four-year rewrite stalled feature work, went nearly a year between releases, and drew public "is this project dead" doubt ([solanky.dev](https://medium.com/@solanky/logseq-migration-journey-challenges-delays-and-hopes-473fa7b8608b), [discuss.logseq.com](https://discuss.logseq.com/t/why-the-database-version-and-how-its-going/26744)); Canopy's incremental, PR-sized, pre-1.0 "freely breakable" posture is the correct antidote and should be protected, especially against large speculative epics (the WASM plugin host, the query engine) becoming their own multi-year freezes
- **Do not let the canonical store become opaque and the portable export lossy** — Logseq's backlash was as much about lossy Markdown export as about the file→DB move ([kompozy.io](https://kompozy.io/news/logseq-2-0-db-version-beta)); Canopy's log is lossless and portable by construction, and the discipline is to keep it that way when snapshot/compaction optimizations arrive
- **Migrate with replayable, validated transforms** — Logseq's import runs schema inference and Malli validation on the way in; Canopy's "schema changes are replayable migration events, validate the graph after projection" is the same instinct and should stay the only migration mechanism ([event-system §4](../design/2026-02-08-event-system.md))
- **Ship the durable-history story Logseq skipped** — Logseq has no general time-travel (only task-status history and a page recycle bin); Canopy's event log gives full history/time-travel for free, a real differentiator to keep as a product feature, not just a debugging aid
